## Project Overview

Dawn is a pragmatic, polyglot build system written in Go. It uses Starlark (a Python dialect) for build definitions (`BUILD.dawn` files) and supports content-based change detection, parallel execution, and watch mode. It is self-hosting--Dawn builds itself.

## Build Commands

```bash
# Bootstrap (build the CLI from source)
go build -o ./bin/dawn ./cmd/dawn

# Self-hosted build (runs default target: lint + build CLI + docs)
./bin/dawn

# Build specific targets
./bin/dawn :dawn          # Build CLI only
./bin/dawn :lint          # Run golangci-lint
./bin/dawn :format        # Run gofumpt on all Go sources
```

## Testing

```bash
# Run all tests
go test ./... -timeout 1m

# Run tests with coverage
gotestsum -- ./... -coverprofile=coverage.out -timeout 1m

# Run a single test
go test ./label -run TestParseLabel -timeout 1m

# Run tests for a specific package
go test ./internal/mvs/... -timeout 1m
```

## Linting & Formatting

```bash
golangci-lint run        # Lint (see .golangci.yml for config)
gofumpt -w <file>        # Format a file
```

Tool versions are managed via mise (see `.mise.toml`): Go 1.24, golangci-lint 2.3.0, gotestsum 1.13.0, gofumpt.

## Architecture

### Core Package (root)

The root `dawn` package contains the build engine:

- **`Project`** (`project.go`) -- Central type that loads, resolves, and executes builds. Manages module loading, dependency resolution (MVS), target execution, caching, and file watching.
- **`function`** (`function.go`) -- Implements the `Target` interface. Each `@target`-decorated Starlark function becomes a `function`. Tracks dependencies, sources, generated files, and environment for freshness checks.
- **`target.go`** -- `Target` interface defining `Label()`, `Run()`, `Check()` etc.
- **`module.go`** -- Represents a loaded `BUILD.dawn` file with its Starlark globals.
- **`events.go`** -- Observer interface for build events (loading, running, completion, errors).
- **`cache.go`** -- Content-based build cache using SHA256 hashes, stored in `.dawn/build/`.
- **`typeenv.go`** -- Builds the `typecheck.Env` used by the LSP and other static analysis consumers.

### Key Subsystems

- **`runner/`** -- Parallel task execution engine with configurable concurrency and gate-based rate limiting. Detects cyclic dependencies at runtime.
- **`label/`** -- Label parsing: `[kind:][project]//[package][:name]`. Labels identify targets across modules and projects.
- **`lsp/`** -- Language Server Protocol implementation for `BUILD.dawn` files: parse/resolve/type-check, diagnostics, completion, hover, signature help, definition, references, symbols, and semantic tokens. Requires a Dawn project (looks for `dawn.toml`); reloads on `dawn.toml`, `.dawnconfig`, and `BUILD.dawn` changes (debounced).
- **`internal/mvs/`** -- Module Version System for dependency resolution (adapted from Go's MVS algorithm).
- **`internal/project/`** -- Parses `dawn.toml` project configuration files.
- **`internal/spell/`**, **`internal/vcs/`** -- Spell-check suggestions for unknown identifiers and VCS integration for module fetching.
- **`pickle/`** -- Serialization format for target metadata (used in build cache).
- **`diff/`** -- Deep value diffing for explaining why targets are out-of-date.
- **`lib/`** -- Starlark standard library modules (`sh/` for shell execution, `os/` for OS operations).

### CLI (`cmd/dawn/`)

Cobra-based CLI. Entry point is `cmd/dawn/main.go`. Key commands: build (default), watch, list, graph, get, tidy, gc, repl, init, lsp (starts the language server on stdio).

### Starlark Integration

Build definitions are written in Starlark. Dawn extends Starlark with builtins like `target()`, `flag()`, `glob()`, `path()`, `label()`, and library modules (`sh.exec()`, `sh.output()`, `os.*`). Builtin bindings in `builtins.go` and `project_builtins.go` are auto-generated by `cmd/dawn-gen-builtins`.

### Build Execution Flow

1. Find project root (search upward for `dawn.toml`)
2. Load and evaluate `BUILD.dawn` modules (Starlark)
3. Resolve dependencies between targets
4. Check freshness via content hashing (SHA256 of sources + environment)
5. Execute out-of-date targets in parallel via `runner.Runner`
6. Persist target metadata to `.dawn/build/` cache

### Test Data

Integration tests use `testdata/` directories with `base/`, `edit1/`, `edit2/`, `edit3/` variants to test incremental build behavior across file changes.
